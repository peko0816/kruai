## 1.1 变异测试：绿色本身不是证据

**做法**：把代码**故意改坏**，跑测试，确认它转红；然后恢复。每一条核心保证各做一次。

一个从未失败过的测试没有证明任何事。它可能断言的是一个恒真的命题、一个被 mock 掉的路径，
或者一个根本没被走到的分支——这三种情况下它都是绿的。变异测试是唯一能区分
「测试通过」和「代码正确」的廉价手段。

**这不是形式主义。C 阶段有四次是变异测试而不是通过的测试发现了问题：**

| 发现 | 如果没做会怎样 |
|---|---|
| SM-2 用 `floor`/`round` 时，ease 触底 1.3 的 interval 永远停在 1 | 最吃力的学习者一边及格一边每天复习，指标上看不出来 |
| C5 的模块 docstring 写错了 DST 语义 | 一段错误的解释会指导后续所有时区相关改动 |
| C7 的「十并发」测试实际没有并发（十次里九次读到已提交的行） | 去掉 `ON CONFLICT` 不会有任何测试转红 |
| G-C 的 `sys.modules` 分层检查拒掉了它应该放行的写法 | 关卡会挡住合法代码，然后被人关掉 |

**两个陷阱：**

1. **`__pycache__` 会伪造结果。** 若变异前后字节长度相同、且恢复发生在同一秒内，
   Python 的 mtime+size 校验会认为缓存仍然有效，于是「恢复后测试依然红」——
   看上去像是变异被捕获，其实测的是旧字节码。**一律带 `PYTHONDONTWRITEBYTECODE=1` 跑。**
2. **变异要改语义，不要改语法。** 改出 `SyntaxError` 的「变异」必然转红，
   什么也没证明。

**写进 PR 的形式**：`变异 A → n 红｜变异 B → m 红`。**有存活的变异就说出来，并补测试**——
C7 的第八条变异第一遍就存活了，那正是最有价值的一次。

## 2. 里程碑验收

### M0 技术验证（外部，不阻塞开发）

|---|---|
| M0-1 中文发音评测 | good 组与 bad 组平均分差 ≥ 15 分，重叠样本 ≤ 20%；音素级 JSON 非空；给出 `ZH_TONE_MODE` 的结论 |

## 3. 什么情况下必须停下来问人

（重复 CLAUDE.md 第 6 节，因为最容易被忽略）

1. **花钱的**：调用付费 API 的默认开关、并发上限、批量任务规模
2. **动钱的**：定价、计量口径、退款与补偿逻辑
3. **对外可见的**：用户文案语气、数字人形象表述、任何品牌相关决定
4. **不可逆的**：数据删除、生产环境迁移、破坏性 schema 变更

其余情况：选最保守方案，实现，记录到 `docs/DECISIONS.md`，继续推进。
