# 真实环境准备清单

**这份文档回答一个问题：代码已经写不动了，接下来要你去办什么。**

到 2026-09-20，`pipeline/` 的 E1–E7 与 `backend/` 的 M2 代码侧全部完成，
`make check` 全绿、全部 provider 为 `fake`。剩下的每一项都需要**真实账号、真人、或真钱**，
代码这边一行也推不动。

---

## 先说结论：钱不是瓶颈，人和账号是

跑一遍真实内容生产的钱，少到不值得开会讨论：

| 项 | 量 | 估算 |
|---|---|---|
| LLM 全量生成 HSK1 | 48 concept × 1 次调用 | **≈ $0.20**（gpt-4.1-mini 档）；旗舰档 ≈ $1.26 |
| 同上，反复重跑 5 次 | | ≈ $1.01 / $6.30 |
| TTS 合成 HSK1 全部音频 | 1296 段、约 1.6 万字符 | **≈ $0.25** |
| Azure 发音评测验证 | M0-1 的样本量 | 免费层（5 小时/月）内 ≈ **$0** |

> 算法：输入约 500 token、输出约 2500 token/concept（拼音和高棉文都很吃 token），
> 按公开单价直算。Batch API 还能再打对折。TTS 按 $16/百万字符。
> 这些是数量级判断，不是报价。

**真正的瓶颈有三个**：ABA 商户资质（走公司与银行流程，最慢）、
高棉语母语者（M0-2 盲评、M1 抽检、km 文案是同一个人能干的三件事）、
以及一批真实的初学者录音（M0-1 没有它就无法校准及格线）。

## 需要你安排的，按紧急程度

### 1. ABA PayWay 商户申请 —— 现在就开始

最慢的一条，因为它不取决于我们。

| | |
|---|---|
| **要办什么** | 柬埔寨公司主体 → ABA 商户账号申请 → 沙箱凭据 |
| **要拿到** | `PAYWAY_MERCHANT_ID`、`PAYWAY_API_KEY`、沙箱 `PAYWAY_BASE_URL`；**并书面确认 `HASH_FIELD_ORDER`（签名字段顺序）与回调字段清单**；确认已开通的支付方式（KHQR / 卡） |
| **为什么要确认字段顺序** | 验签算法对字段顺序敏感，文档版本之间有出入。拿错顺序的症状是「回调全部验签失败」，而那时你已经在排查网络和密钥了 |
| **验收** | 沙箱能建收银台、能完成一笔小额支付、回调验签 SIGNATURE OK |
| **解锁** | M0-3 → D9（真实 adapter，接口与契约测试已就位）→ M2 的收款闭环 |
| **成本** | 商户申请费用按 ABA 政策 |

### 2. 高棉语母语者 —— 一个人解锁三件事

| | |
|---|---|
| **要办什么** | 找 1 位（最好 2 位）高棉语母语者，能读基础中文或英文对照 |
| **三件事** | ① M0-2 的 TTS 盲评（需要 ≥2 人独立评分）② M1 的 10% 内容抽检 ③ `locales/km.json` 与课程标题的文案 |
| **工作量** | 盲评 10–15 段音频，约 1 小时／人；抽检约 120 行，按每行 1–2 分钟算 2–4 小时；文案按 key 数量另计 |
| **交付物** | 盲评：自然度 / 可懂度 1–5 打分表；抽检：填好 `verdict`、`comment` 两列的 CSV（`make review` 导出，判定三档 `ok` / `awkward` / `wrong`） |
| **验收** | 盲评均值 ≥ 4 且无致命发音错误；抽检合格率 ≥ 90% |
| **额外价值** | 他是**唯一**能发现词表里「形近且同音同调」转录错误的人（见 D-092），请把这一类列为优先检查项 |

### 3. Azure Speech 账号 + 一批真实录音 —— M0-1

| | |
|---|---|
| **要办什么** | Azure 订阅 → Speech 资源（建议 East Asia / Southeast Asia 区）→ 拿 `AZURE_SPEECH_KEY` + `AZURE_SPEECH_REGION`。免费层 F0 足够 |
| **还要录音** | 同一批 HSK1 句子（20 条左右），两组人各录一遍：**good 组** = 中文说得好的人；**bad 组** = **真实的柬埔寨初学者** |
| **为什么 bad 组不能找人假装** | 评测模型对「装出来的错」和真实 L1 口音的反应不一样。用装的样本校准出来的及格线，上线后会系统性偏高或偏低，而这件事要到有真实用户数据时才会发现 |
| **验收** | good/bad 平均分差 ≥ 15、重叠样本 ≤ 20%、音素级 JSON 非空；并据此给出 `ZH_TONE_MODE` 的结论（音素串是否自带声调数字） |
| **解锁** | E9（真实 scoring adapter）+ **一次连带的参数重标定**：不能只调 `SCORING_PASS_THRESHOLD`，必须连同 `MASTERY_DELTA_BASE` 与三个 item 权重一起重标（遗留约束 **L-7** 算过：按当前默认值，`ease_factor` 会在掌握度还很低时就触底，间隔重复几乎不生效） |
| **我需要的** | 录音文件（wav/mp3 均可）+ 每条对应的参考文本。拿到 key 和样本后，我写验证脚本跑出统计表并落 `docs/m0-1-scoring.md` |

### 5. TTS 选型 —— M0-2

| | |
|---|---|
| **要办什么** | 候选三家的账号与 key：Azure（复用 3 的资源）、Google Cloud TTS（需 GCP 项目 + 服务账号 JSON）、ElevenLabs |
| **盲评素材从哪来** | **不能用还没写的课程文案**。用 MoEYS OER（oer.moeys.gov.kh，CC-BY 3.0，在 R7 白名单内）的公开高棉语段落，取 10–15 条，三家各合成一遍，隐藏厂商名后让母语者打分 |
| **验收** | ≥2 位母语者独立盲评，自然度与可懂度均值 ≥ 4，无致命发音错误；产出 `docs/tts-decision.md`（含逻辑音色 → 厂商音色的映射表） |
